# Joint behavioral assessment contract

Prompt 3.32 uses two serial model requests for one new assessment: a complete joint draft, then a complete editable replacement. Both choose optional source accounts, observation purposes, verdict, mappings and hypotheses. The draft is private provisional evidence. It is never a normal assessment, completed cache hit, scoring input or fallback. A legal, validated answer does not establish usefulness. This implementation has no model acceptance or release approval.

The draft wire is `joint-answer-draft-1`; the replacement wire is `joint-answer-revision-1`. The durable topology is `full-joint-draft-revision-1`, ledger schema 3. The canonical final result remains `behavior-3`, with the original fixed claims, citations, source tuples, roles, support constraints and uncertainty. Prompt, generation, topology, configuration, tokenizer, source and exact request identities distinguish this work from historical contracts.

## Complete input and legal choices

Each optional observation maps its original offered key to `omit`, `detail`, `support`, or qualifying `counterevidence`. Missing keys omit. Detail and support materialize the identical complete original finding and citations. Counterevidence must be the original offered positive opposing context. There are no authored reasons or comparison witnesses. Old wires, duplicate JSON members, unknown fields or references, nonfinite values, unsupported verdicts and incorrect replacement bindings reject; no response repair is used.

All original groups, observations, purposes, mapping slots and hypotheses remain selectable. All accounts may be omitted, all generic findings remain legal, and replacement can add or remove any choice. Accounts are not frozen by the draft. The original combined 12 observation,12 ATT&CK,6 D3FEND and group/hypothesis bounds remain; no lower cap, deduplication, usefulness filter, source withholding or forced support is added. Malicious requires the original complete support pair in findings, without forcing that verdict. Benign requires fresh cited positive context. Empty intent/automation stays unknown with confidence 0.

Both requests contain the same complete original packet, events, context, history, candidates, provenance, offers, roles, support and uncertainty. Reversible factoring preserves every original value and type, including objects resembling reference markers. Replacement additionally receives the instantiated draft choices and the existing renderer's account, interpretation and uncertainty. Original group references resolve complete source tuples and event rows. Choice indices use the original table order and preserve selection order; they are a fit encoding, not a ranking. The binding digest is inserted literally after factoring so equality with a source string cannot alter source meaning.

Rendered accounts were already available among original offers. The additional decision is not new independent evidence, and agreement between the two passes does not establish accuracy. Input is not execution, capture is not transfer, and status or a firewall drop is not independent attack proof. EDL Manager retains scoring and enforcement ownership; Wazuh remains a source.

Each complete user message must fit 18000 bytes and each full request 65536 bytes. The operator-pinned tokenizer must verify input plus the complete 1800 output reservation and 1 EOS under 8192 tokens for each request. Runtime never queries model metadata or downloads assets. Oversize or unverifiable complete input stops before that request's entry, without trimming, smaller allowances, refill or fallback. A rejected, incomplete or length-terminated draft never permits replacement.

## Owned lineage and immutable decoding

An immutable plan binds source/configuration/model/tokenizer identity and the exact draft request. Replacement is derived only by the owning ledger from its own durable accepted draft capture. There is no raw-draft argument on the runtime revision API. Capture files must match the immutable in-memory owned stream as well as their durable request/binding/finalization records. Historical or caller-provided drafts are not live repair inputs.

The receipt binds parent identity, exact raw draft hash, canonical hash, complete rendering hash and source identity. The ledger binds the exact replacement body and its input key; the final decoder is immutable and bound to that request and draft digest. Both stages use the pure original fixed-claim materializer and validators directly. Cached schema/tables support decoding without request re-preparation or tokenization. The final owned raw capture, canonical result and rendering are also validated and retained before durable acceptance.

## One deadline, two reservations and one final result

One configurable deadline, at most 180 seconds, covers both preparations, admissions, connections, streams, parsing, validation, captures and finalization. It never resets between stages. Where the 180-second admission protocol is enabled, each admission wait is at most 15 seconds and no greater than remaining time. Nested bounded work remains under the original controller deadline. Cancellation closes watched client I/O and fences late work; client close does not prove remote compute stopped.

One short FULL-sync SQLite transaction predeclares exactly two children and reserves two units atomically. Claiming binds a request; each actual dispatch entry spends one unit exactly once. Each entry rechecks current quota, including the entire remaining reservation and competing holds. UTC day rollover changes the day charged for that entry, without reopening logical work. Spent or uncertain entries are never refunded. Only never-entered reservations are released.

There is no retry, partial resume, parallel model call, third child or accepted draft fallback. Enabled state, configuration, source, packet, registry, tokenizer, request, ownership, lease, budget and dispatch day are checked at the relevant boundaries. A failed or uncertain logical source/configuration remains consumed even after expiry, process restart, relocation or a new quota day. Only an already validated final outcome may be persisted idempotently without new inference or duplicate scoring/publication.

Accepted child and final-parent authority survive a lost terminal acknowledgement. Bounded read-only reconciliation copies existing committed authority; it never creates a new late acceptance. Failure cleanup cannot downgrade an already completed parent or overwrite an accepted child.

Private Unlimited stays Unlimited. Community remains AI-off with the existing finite 24 daily request default. The existing finite two-entry cycle ceiling admits one complete two-request assessment, and does not start a new parent with only one cycle unit left. Failures and UTC rollover prevent any fixed daily completed-assessment guarantee. Provider backoff, native fallback, pilot limits, whitelist/crawler protections and source ownership remain in force.

## Legacy preservation and private evidence

Migration preserves actual installed 3.17 assessments, usage and version 1 journals, plus schema 1/2 pipeline rows, request receipts, spent charges and accepted outcomes. Distinct old source/configuration owners are retained; one completed owner cannot hide an unresolved owner. Legacy incomplete generation is fenced, unentered holds released, and old partial claims never become new grants, resumable work or completed cache entries. A validated old final-pending result may be saved in its original format. Unknown schemas require review. The historical [account-then-selection contract](TWO-STAGE-ANALYSIS.md) is not a fallback execution path.

Per-parent private evidence has separate `stage1` and `stage2` directories. Bounded raw responses, exact requests, receipts and as-of accounting are retained with restrictive permissions, exclusive writes and durable flush. Credentials, authorization headers and provider configuration are never captured. Provisional or rejected JSON, prompts, bindings and traces do not appear on ordinary product screens. Snapshot/close failures cannot publish a completed assessment. Validation sidecars are separate from committed child/assessment authority.

Request receipts retain stage-specific counters, cache accounting, backend timings, first-content measurements, conflicts, missingness and known failures. The parent distinguishes planned requests, observed transport starts, charged entry units and one assessment. Unknown values never become zero; a second claim's failure never inherits the draft's counters or request ID. Parent sums require known constituent counts. Whole-assessment duration and summed request duration are never relabeled as first-content latency.

Explicit accounting reconciliation appends supplemental evidence with provenance/as-of time, adding no request, accepted output, charge or deadline extension. It does not rewrite original authority. Private draft/final captures follow the existing retention decision: retained assessments and pending/review/uncertain work keep evidence; expired completed/failed work can compact to permanent consumed tombstones before bounded filesystem cleanup outside the writer transaction.

## Verification boundary

Both editions require full isolated regressions and actual application tests for lineage, migration, quota races, rollover, crashes, cancellation, deadlines, captures, late accounting, pending saves and child/parent lost acknowledgements. Exact-source proofs must reconstruct both complete inputs and bound all legal provisional selections, including order and confidence choices. Synthetic reachability and compatibility are not actual model selection or native grammar proof.

The unchanged 21-case/42-pair semantic gates require every original control, neutral and HTTP account, all eight typed findings and strict reduction in each locked noise cell in each round, without fresh generic regression or meaning loss. The unchanged 3.28 baseline cannot reserve the full allowance in 14 of 21 cases per edition and remains a limited historical arm. Reused unblinded development data establishes no independent intent truth or calibration.

Two candidate calls replace one. Any future 42-baseline/84-candidate comparison requires a separate 126-maximum topology, review and fresh authorization. All prior executions remain closed. Native grammar, actual model quality, production migration/performance and delivery remain unproven. Existing production SQLite contention is an unrepaired delivery dependency. This document authorizes no model call, deployment, unattended operation or enforcement change.
